# v0.7.0 — True 4K lock + site-style subtitle engine

Round notes (root causes found in the user's fresh log.txt + full source audit). Everything below is verified against the captured behavior of vidfast.vc / vidcore.io / mappletv.uk (see `work/findings-subtitles-4k.md` research in the build sandbox and `research-*.md` here).

## 1. "4K doesn't look like 4K from vidcore/vidfast, video looks crunched"

**Root cause (confirmed from logs):** the app *did* resolve the master playlist
(`Verify: OK m3u8-master`) and the ladder *did* contain
`2160p avc1.640033 @ 16.2 Mbps`. But `applyQualityMode(MAX)` only set a
**ceiling** (`setMaxVideoSize(3840, 2160)`). The actual choice stayed with
AdaptiveTrackSelection, which needs roughly `variantBitrate / bandwidthFraction`
of measured bandwidth before it climbs — with `bandwidthFraction = 0.55` and a
25–30 Mbps line, the 16.2 Mbps 2160p variant needed ~29.5 Mbps effective →
**the player silently sat at 1080p**. Every mode (auto/lock, deep/balanced)
was just a different ceiling, so they all looked identical — "no matter what I
set, it looks the same."

Two aggravating factors:
- the stall watchdog silently re-capped quality to 1080p after a 12s stall
  (visible in the log as `quality mode -> CAP_1080` at 13:14:31);
- Mapple happened to cross the ABR threshold (its estimate was higher through
  its proxy), which is why Mapple "looked like 4K" — the same ladder, just an
  ABR coin flip.

**Fix:** MAX mode is now a REAL lock —
`TrackSelectionParameters.setForceHighestSupportedBitrate(true)` (plus the size
ceiling). The top rendition the codecs honestly support is pinned from the
first segment, and switching the setting mid-playback re-selects the track
**instantly** (parameters are applied live, no reload). The label is now
"4K lock — always top rendition (2160p)".

**Also fixed:** the stall watchdog no longer silently lowers quality in lock
mode (it reconnects at the same quality instead; only the *Auto* adaptive mode
may still trade quality for smoothness). Buffer profiles (Smooth/Deep/Balanced)
now only change how much is buffered, never what you see.

## 2. Subtitles turned off after switching source

**Root cause chain:** on the first stream, `maybeAutoSelectEmbedded()` picked
the (sidecar-induced) text track and **nulled the active sidecar**; the
`preAttachTried` / `embeddedAutoTried` flags were never reset when a new
source was resolved, so the new MediaItem was built with no subtitle attached
and nothing re-armed it — subtitles stayed off until manually re-selected
(the user's log shows exactly that manual re-selection after the Mapple
switch).

**Fix:** complete rework of the subtitle pipeline (below) — the sticky
language survives source switches; the sidecar cues are re-armed from the new
source's own listing (or kept from the same title if the download fails), and
only the per-source sync delay changes.

## 3. Subtitle engine — site architecture, native rendering

The three sites all do the same thing (mined from the user's saved pages in
zip.zip): download SRT/VTT, parse to cues, **render with their own overlay**
(video element untouched), apply a user-adjustable timing offset, and style
size/color/background themselves. The app now mirrors that exactly:

- `Subtitles.kt` — SRT/VTT parser (BOM/CRLF/WEBVTT/NOTE tolerant, `,` and `.`
  ms separators, HTML/SSA tag stripping, ad/credits cue scrubbing — same
  heuristics the sites use).
- The sidecar is **no longer attached to the MediaItem** (this also
  permanently removes the old file://-sidecar-fed-to-OkHttp RUNTIME_CHECK
  class of crashes). Cues are rendered by a Compose overlay
  (`SubtitleOverlay`) driven by a 100 ms tick.
- **Switching subtitle language is instant** — no media-item restart anymore.
- **Subtitle sync:** each source's video copy is trimmed differently, which
  is why the same subtitle file runs 2–6 s early/late depending on the
  source. Per-provider persisted delay (mapple's `timingAdjustment`
  equivalent): nudge −/+0.25/0.5/1 s from the player's "Sync" button
  (instantly applied, no reload), persisted per source; also editable in
  Settings. `+` = subtitles appear later (the fix when they run ahead).

## 4. Subtitle appearance (was: "too large, no options")

Old renderer was PlayerView's built-in SubtitleView with fixed styling
(~5.3% of height base). The new overlay defaults to ≈4.2% of screen height and
is fully customizable in Settings → Subtitles: size (80/100/125/150%), color
(white/yellow/cyan/silver — the sites' palette), background darkness
(0/25/55/80%).

## 5. Build workflow

`.github/workflows/build.yml` was audited during this round (a display
artifact initially made the trigger look mangled — verified via the GitHub
contents API + git blob hashes that it is correct): pushes to `main`, `v*`
tags, PRs, and manual dispatch all build, and the rolling "latest" release
is re-published on every main push.

## Note on the log.txt artifacts

The `TurboPrefetch prefetch miss … InterruptedIOException` bursts in the user's
log are benign: they are in-flight prefetch tasks being interrupted when the
player is rebuilt (source switch / recovery) — exactly 4 at a time (the worker
pool size). The prefetch engine itself parses and warms segments normally.

## What to expect when testing

1. Play anything on vidcore/vidfast with quality = "4K lock": the stats
   overlay should immediately show `2160p` (and "4K 2160p" badge), not climb
   from 1080p.
2. Switch quality mid-playback Auto ↔ 4K lock: the rendition change should
   be visible instantly (next segment boundary), no reload/re-resolve.
3. Switch source mid-playback: subtitles stay on (same language), only the
   per-source sync delay changes.
4. Subtitle sync: if subtitles lead/lag, use the Sync button (+ = later,
   − = earlier); the value sticks per source.
5. Subtitle size: Settings → Subtitles → Text size; default is smaller than
   before.
6. Logs now carry: `4K LOCK engaged`, `overlay subtitle … armed: N cues,
   sync=…ms for <source>`, `sync delay for <source> -> …ms`.
