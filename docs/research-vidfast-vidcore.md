# Vidfast.vc stream resolution — RE findings (Task 2-a) — COMPLETE

## Executive summary
- vidfast.vc (and vidcore.io, same codebase, different constants) resolves streams via a **single POST API** on its own origin whose URL path carries an **encrypted, session-bound, one-time payload**. The response is an **encrypted blob** (custom envelope: ephemeral X25519-style key + AES + HMAC + Ed25519 signature, per string table) that is decrypted/executed inside a **JSVMP-sandboxed VM** inside player chunk 586. The decrypted result (`h[0]`/"dr" array) is the player config containing the direct **m3u8/mpd/mp4 URL**.
- **The request payloads cannot currently be forged with plain HTTP calls** — they are generated by ~5KB of obfuscated VM code (string-array + crypto ops). Old payloads replay → HTTP 500. The m3u8 URL itself works from any client once obtained (token in query `?s=...`, expires — 403 after ~1h+).
- **Practical Android approach**: run the page/JS in a headless WebView (or port the VM), let it produce the m3u8, then hand to ExoPlayer. Subtitles are available via a **token-free** endpoint (`/wyzie`) that works with plain curl.

## 1. Exact HTTP chain (from live browser capture, work/vidfast-live/capture2.jsonl + capture-tv.jsonl)

POST https://vidfast.vc{BASE}/2sYX823A4fc/{ENC_PAYLOAD_2}     ← (issued around same time; likely session/register or heartbeat; 2-3.5 KB response)
POST https://vidfast.vc{BASE}/8ZFavsHEv8c/{server.data}       ← "get player config" (server.data = token from server list)
     → 200, body = encrypted blob (0.7-10 KB) → VM sandbox #2 decrypts → config:
       { url: <master.m3u8 | .mpd | .mp4>, tracks: [subtitles], tmdbId, title, poster,

## 3. Payload structure (request path segment)
Decoded (base64url) sample from capture:
```
hex:   56 31 38 53 ("V18S" magic) 01 12 01 01 00 2b 00 20 00000056 00000083 00000083 10 0c 10 02 ...
ascii: V18S ...... + len-prefixed string "8rGefdRb2G-BTMM0lBAGdBh4L3KzbIrX_btZOXsNxjc" + "8.212.10.159" (client IP!) + encrypted tail (signature/box)
```
- `K57NKISb...`-style payloads (43-44 char common prefix across sessions) = same ephemeral-key prefix scheme.
- Payloads are **single-use/time-bound**: replaying a captured payload → HTTP 500 (verified today). Same prefix reused within same session/time window → deterministic client key derivation, but tail differs per request (nonce/counter).
